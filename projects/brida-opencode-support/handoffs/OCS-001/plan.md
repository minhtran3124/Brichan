## Design — carried unchanged from v3

- D1 **Pure mode + screen fallback.** Every guarded process uses `--pure`; Herdr lifecycle uses screen-manifest fallback; plugin/tool non-execution is proven only by side-effect markers, never by `debug config` list contents. **Corrected in v9 after live probe L4 falsified the earlier claim:** `--pure` does **not** suppress a project-local `.opencode/plugin/*.js` in a real TUI session. L4 proved this reproducibly on a pristine project — no prior provider run, no `node_modules` — and proved that `debug config` is not a valid control for it, because only a real session loads plugins. `--pure` is therefore retained for its other effects but is **never** cited as the control for plugin non-execution. The authoritative control is D8's independent scan, which refuses before any provider process starts.
- D2 **All-prefix scrub.** Shim `brichan-opencode-exec` removes every inherited `OPENCODE_*` key (including `OPENCODE_CONFIG_DIR`) without inspecting or logging values.
- D3 **Pinned transport.** Routed model/effort become `agent.brichan-primary.model`/`.variant` inside compact `OPENCODE_CONFIG_CONTENT`; this is an intended input, not globally authoritative because org/well-known and managed sources merge later. Launch argv is `opencode --pure --agent brichan-primary` (TUI); top-level `--variant` never emitted. Legacy `-m` is consumed and validated by Brichan into the agent config and never forwarded as provider argv.
- D4 **Pre-Herdr worker gate.** Named/default/legacy OpenCode worker requests against any target containing `.brichan`, healthy or not, fail before Herdr mutation. Installed dispatcher and packaged resources remain Codex-only.
- D5 **Parity/inventory.** Both console scripts packaged and exposed by `scripts/install-brichan`; installed-dogfood smoke; repository-path inventory; byte-identical Codex/Claude argv; optional schema-v1 OpenCode coordinator entry.

## Design — new in versions 6 and 7

- D6 **Version gate.** `opencode --version` must equal `1.18.12` exactly, checked before any config/tool resolution or provider spawn; mismatch refuses with an owned error. The isolation contract is source-line specific and re-verified on any version bump. **Ordering resolved in v7 (closes the v5 L4 / v6 finding-1a gap):** `--version` is source-verified not to reach any migration path, so it may legitimately run before D12's scan. `index.ts:51` binds `--version` as a yargs boolean flag; `tui.ts:73` registers `TuiThreadCommand` as the default `"$0 [project]"` command, so `yargs-factory.ts:2132` dispatches the default command before the version-exit block in that frame, and the recursive re-parse it triggers hits `yargs-factory.ts:2185-2189` and calls `process.exit(0)` via `yargs-factory.ts:734,736` (`#exitProcess` defaults true at `:185`; opencode never calls `.exitProcess(false)`). That synchronous exit precedes `applyMiddlewareAndGetResult` (`command.ts:484-538`), so the global middleware, `TuiThreadCommand.handler`, `TuiConfig.get()`, and therefore `config/tui.ts:173-174`'s `migrateTuiConfig` never run. No `tui.json`, no `.tui-migration.bak`, no in-place key strip. Evidence: `/tmp/brichan-ocs001-v6-source-verify.md`, traced against `anomalyco/opencode@v1.18.12` and its pinned `yargs@18.0.0`. The yargs dependency makes this conclusion version-pinned in **two** packages: any bump of either re-opens it.
- D7 **Custom-tool root isolation (closes C1).** Shim sets `OPENCODE_DISABLE_PROJECT_CONFIG=true` (removes project `.opencode` root); creates a fresh empty per-launch dir as `XDG_CONFIG_HOME` (neutralizes global XDG root, hides global OpenCode config/AGENTS); sets `OPENCODE_TEST_HOME` to a second fresh empty per-launch dir (narrow source-backed `Global.Path.home` override neutralizing the home-dot OpenCode root `<home>/.opencode`); leaves `OPENCODE_CONFIG_DIR` absent. `HOME` is never overridden; `XDG_DATA_HOME`/`XDG_STATE_HOME`/`XDG_CACHE_HOME` are never touched, so real data/state/cache and the OpenCode auth file keep resolving through the real home. Isolation changes config and home-dot discovery only.
- D8 **Independent discovery preflight.** Before spawn, Brichan itself resolves all four v1.18.12 discovery roots — isolated XDG config root; project `.opencode` upward walk cwd→worktree (scanned redundantly despite D7); `<OPENCODE_TEST_HOME>/.opencode`; `OPENCODE_CONFIG_DIR` (must be unset) — and globs `{tool,tools}/*.{js,ts}` **and `{plugin,plugins}/*.{js,ts}` (extended in v9)** in each, singular and plural, following symlinks. Any match, any symlink inside an owned isolated root, or a set `OPENCODE_CONFIG_DIR` refuses before provider startup. **Extended in v12 to close the last hand-listed surface.** Version 11 made D12's config-file scan set source-derived and drift-tested, but left D8's own directory globs — the `{tool,tools}` and `{plugin,plugins}` families — as a hand-maintained list with no equivalent test. That is the same exposure this project has already paid for four times, one surface over, and the implementer raised it rather than leaving it buried. D8's glob set must therefore be derived from the provider's own per-root directory-scan implementation at the pinned version, carried in code as an explicit source-cited list, and covered by a drift test of the same shape as D12's: the scanned set must equal the documented derivation, so a provider bump that adds a scanned directory family or a new executable extension fails a test rather than silently opening a hole. The drift test must fail on an ADDED path in the provider's set, not only on one removed from ours; catching deletions alone would not do the job this clause exists for. **The `{plugin,plugins}` scan is the sole control for project-local plugin execution** and must not be relaxed on the argument that `--pure` or config isolation already covers it: L4 proved both of those false for this vector. A plugin match refuses with the same key-path-only diagnostic shape as a tool match, naming the Brichan-discovered path and no provider output.
- D9 **Trust boundary.** Target repository `AGENTS.md` and its project skill `.agents/skills/herdr-orchestration/SKILL.md` are trusted, user-authorized repository input per `decisions.md`; the no-secret claim is scoped accordingly. Shim sets `OPENCODE_DISABLE_CLAUDE_CODE=1`. `agent.brichan-primary.permission.skill` is exactly the ordered rules `{"*":"deny","herdr-orchestration":"allow"}`; global home/XDG skill roots are isolated by D7, so only the required project orchestration skill is agent-available. The guard config includes exactly one absolute, Brichan-computed `AGENTS.md` path in `instructions`; relative, home, remote, and extra instruction entries are rejected. Global OpenCode config/AGENTS are hidden by isolated `XDG_CONFIG_HOME`/`OPENCODE_TEST_HOME`. **Authoritative skill probe, named in v7 (closes the v5 L3 / v6 finding-1b gap):** the agent-scoped, post-permission semantic is `Skill.available(agent)` at `skill/index.ts:310-315`, which filters discovery through `Permission.evaluate("skill", skill.name, agent.permission)`. **No CLI command prints that set** — `opencode debug skill` (`cli/cmd/debug/skill.ts:6-14`) calls `Skill.all()` (`skill/index.ts:301-304`), which is raw discovery with no agent argument and no permission filtering, and `opencode debug agent <name>` resolves tool permissions only, never skills. The two-part authoritative check is therefore: (i) **discovery precheck** — sanitized `opencode --pure debug skill` must enumerate at most the project `herdr-orchestration` skill plus the built-in `customize-opencode`; any other entry refuses before spawn; and (ii) **availability evidence** — E1's live in-session check of the `<available_skills>` block that `session/system.ts:98-101` builds from `Skill.available(agent)`, which is the only observable rendering of the post-permission set. Clause (i) is necessary but not sufficient and is never cited as availability proof; clause (ii) is the acceptance authority. Evidence: `/tmp/brichan-ocs001-v6-source-verify.md`.
- D10 **Single primary agent (closes H2).** Guard config disables all five built-in primaries — `build`, `plan`, `compaction`, `summary`, `title` — via `agent.<name>.disable=true` and sets `default_agent="brichan-primary"`; final state must show exactly one primary. Keybind backstop: shim writes `<XDG_CONFIG_HOME>/opencode/tui.json` containing exactly `{"keybinds":{"agent_cycle":"none","agent_cycle_reverse":"none"}}` into its owned isolated root and preflights that file before spawn. Debug config must omit `keybinds`; acceptance relies on the owned TUI file plus only-one-primary state and live probe L5.
- D11 **Installed console gate (closes H3).** Any direct `brichan-opencode` invocation other than `--help`/`--version` whose resolved target contains `.brichan` refuses before preflight and provider spawn unless the running package positively identifies the Brichan source checkout (exact package-marker check: `pyproject.toml` project name plus `src/brichan` layout at the resolved root — not the `AGENTS.md`+`bin/` heuristic).
- D12 **Migration-write gate (closes H3).** Before any provider process except the source-verified D6 version-gate spawn (see D6), scan every config file the provider itself can read. **Restructured in v11 after a fourth vector.** Versions 9 and 10 each patched one newly-discovered location — first `{plugin,plugins}` directories, then `plugin` keys in plain ancestor `opencode.json` — and each time a further location surfaced. A project `.opencode/opencode.json` executed a declared plugin under the version-10 guard, because D8 globs only that root's `{tool,tools}`/`{plugin,plugins}` subdirectories while D12 walked plain ancestors without ever appending a `.opencode` segment. Patching locations one at a time is not converging, so the scan set is no longer hand-listed. **The scan set is derived from the provider's own configuration-discovery implementation at the pinned version, and the implementation must carry that derivation as an explicit, source-cited list.** A test asserts the scanned set equals that documented list, so a future provider bump that adds a discovery path fails the test rather than silently opening a hole. At minimum the set covers, for every discovery root and every ancestor up to the bound: `opencode.json` and `opencode.jsonc` in the directory itself, and the same two filenames nested inside a `.opencode` directory. If the source enumeration yields more, the enumeration wins, not this sentence. **It did, twice more.** Round 8's key derivation found four execution keys where two had been hand-listed, and round 12's determination found the TUI document (`tui.json`/`tui.jsonc`) to be an executable surface rather than presentation-only state, bringing the derived config-source set from seven entries to eleven. Both were found by derivation before any live failure, which is the behaviour this clause exists to produce. Round 12 was gated on a determination rather than implemented on request: widening the scan blindly risked refusing D10's own owned `tui.json` backstop, so the question 'can this document reach an executor' was settled from source first, and the answer happened to be yes. Live-verified afterwards: a `tui.json` carrying an execution key refuses, and a clean checkout still launches. **The execution-key set is derived too, added in v13.** Versions 11 and 12 derived *which files* and *which directories* the guard inspects, but the set of keys applied to each file — `plugin`, `plugins` — remained hand-listed, which is the same exposure a third time and was again raised by the implementer rather than by a reviewer. The keys must be derived from an enumeration of every configuration key at the pinned version whose value becomes a module specifier the provider will load, carried in code with its source citations, and covered by a drift test that fails when the provider gains such a key. **The derivation found four, not two: `plugin`, `plugins`, `provider`, `providers`** — all four bypass the merged document. `plugin` and `plugins` had been hand-listed; `provider` (`provider.<id>.npm`, `provider.<id>.models.<id>.provider.npm`) and `providers` (`providers.<id>.api.package`) were **not refused by the pre-round-8 guard**, which is precisely the sixth vector the round existed to pre-empt. Their evidential status differs and is recorded rather than flattened: `plugin` is live-confirmed to execute under a guarded launch; `plugins` is refused on a source argument that live testing did not reproduce on this version; `provider` and `providers` are refused on the source derivation, with **exploitability neither established nor refuted** — a coordinator probe placing a local file at `provider.<id>.npm` did not execute at startup, but no firing positive control was achieved for that key, so that silence is not evidence either way. Provider loading appears lazy rather than startup-time, and the guard pins the routed model, so a hostile provider is unlikely to be selected; the refusal is retained as fail-closed regardless, because the cost is two key names and the failure mode is refusal. D13's positive allowlist cannot substitute for this: D12 exists precisely for loaders that bypass the merged document, so a key that never reaches the merge is invisible to the allowlist by construction. If any parsed config contains `theme`, `keybinds`, or `tui`, refuse with key-path-only diagnostics; this prevents provider TUI migration from rewriting config or creating backups outside the owned isolated root. **Extended in v10 to `plugin`, which is an execution key, not a migration key.** A live probe on the pinned 1.18.12 showed a project `opencode.json` carrying `"plugin": ["./declared.js"]` executes that file under the full guard. D8 cannot cover it because the declared path is arbitrary and need not sit under `{plugin,plugins}`; in the reproduction it was at the project root. D13's allowlist cannot cover it either, and this is the load-bearing point: `OPENCODE_DISABLE_PROJECT_CONFIG=true` **does** correctly keep the project array out of the merged document — `debug config` reports `plugin: []` — while the plugin loader reads the project `opencode.json` directly and bypasses the merge entirely. Value-gating `plugin` in the allowlist would therefore inspect a value that is already empty and prove nothing. A filesystem scan of the discovered config files is the only control that sees what the loader sees, which is why this clause and not D13 owns it. The refusal covers **both spellings, `plugin` and `plugins`**, but their evidential status differs and the difference is recorded rather than smoothed over. `plugin` is a **live-confirmed** vector: it executed under the shipped guard on 1.18.12, and at provider level in an unguarded control. `plugins` is refused as **defence in depth on a source argument that live testing did not reproduce**. The argument, from the implementer, is that `v1/config/migrate.ts:30-32` treats a top-level `plugin` as a v1 marker and `migrate()` writes it into the v2 `plugins` field, while a config carrying only `plugins` decodes straight to that same v2 field which `config/plugin/external.ts` imports. A coordinator probe on 1.18.12 tested exactly that: an unguarded run with only `"plugins": ["./declared.js"]` did **not** execute the file, while the identical project using `plugin` did. So on the pinned version the v2 spelling is not a reachable executor, and refusing it buys future safety if the v2 path becomes active, not a closed hole today. It is kept because the cost is one key name and the failure mode is fail-closed. The refusal uses the same cwd-to-filesystem-root walk and the same key-path-only diagnostics as the migration keys.

Refuse any mismatch. ## Risks and rollback

- `OPENCODE_TEST_HOME` is an internal, undocumented override: acceptable only under the exact D6 pin (decisions.md); any OpenCode upgrade re-opens the isolation review before the pin moves.
- D6's no-migration conclusion depends on `yargs@18.0.0` internals as well as OpenCode's own source, and was verified by reading pinned TypeScript rather than the published JS build. A bump of either package re-opens it, and the D12 scan is retained as the standing control regardless.
- **Closed by determination and live probe: the `npm.install` fan-out is not a further vector.** Installing a package runs lifecycle scripts by subprocess rather than by `import()`, which is outside the closure argument's method boundary, so it needed settling separately rather than assuming. It is closed for **two independent reasons, either sufficient alone**: D7's isolation means the install's working directory and npm-config cwd can only be a Brichan-owned scratch root, never anything under the project tree; and `npm.ts` hardcodes `ignoreScripts: true` as the last key of the Arborist constructor literal, which no `.npmrc` can override — verified against the pinned `@npmcli/arborist@9.4.0`, whose options are set once at construction and never remerged at `reify()`. A coordinator live probe corroborated this independently with a **firing control**: the install demonstrably runs and creates `node_modules` in the owned isolated root, installs the fixed `@opencode-ai/plugin` at the pinned version, and ignores a project `.npmrc` carrying a hostile `registry` and `script-shell` — proven by the install succeeding against the real registry when the planted registry was an unreachable port.
- **Recorded, different in kind and not a project-controlled execution vector:** the ESLint and Elixir LSP auto-downloaders do run installs without ignore-scripts protection, but always against the upstream tool's own manifest from a fixed URL. A project can *trigger* those installs; it cannot steer what they install. That is a supply-chain exposure inherited from the provider, not a hole in this guard, and it is recorded rather than dismissed. Whether those installers fire during a typical Stage 1 session was not confirmed live, and does not change the determination.
- **`debug config` is not a reliable oracle for provider behaviour, and this is now a standing rule for this provider rather than a caution.** It reported no plugins while a directory-discovered plugin executed, and it reports `plugin: []` while a config-declared plugin executes. Every non-execution claim must rest on side-effect markers observed in a real session, exactly as D1 required from the start. No future clause may substitute a `debug config` reading for marker evidence.
- **Closed by probe: `mcp` is not a second vector of this shape.** With a valid absolute-path marker and a firing negative control, the shipped guard did not spawn a project-declared MCP server on 1.18.12, reproduced from a verified-zero baseline. `plugin` is the special case: its loader reads the project `opencode.json` directly, while `mcp` resolves from the merged document that `OPENCODE_DISABLE_PROJECT_CONFIG=true` correctly empties. The earlier L4 MCP marker was invalid and its result was discarded rather than counted.
- **The mechanism of the L4 failure has a well-evidenced hypothesis but is not proven.** The final review and remediation round 4 identified a third plugin path, `ConfigExternalPlugin.Plugin` in `packages/core/src/config/plugin/external.ts`, which carries no pure-mode gate — unlike `plugin/index.ts` and `plugin/tui/runtime.ts`, which do. That is sufficient to produce the L4 observation. It is **not** established that this path, rather than a fourth, actually fired; confirming it needs live TUI instrumentation. Recorded as a candidate explanation, explicitly unconfirmed. The design does not depend on the answer: D8's Brichan-side scan is the control precisely because it does not require the provider to honour its own flag, and it must never be relaxed on the theory that `--pure` suffices.
- **D8 now carries an unstated-until-now precondition: a Git worktree must exist.** Round 4 closed the ancestor-directory escape by refusing to launch when no `.git` is found at or above `cwd`, rather than by widening the walk to the filesystem root to match the provider's own behaviour (`packages/core/src/project.ts:110-120`). Refusing is right for a checkout-oriented launcher and is the safer default, but it is a trade-off: if a later stage relaxes the checkout orientation, this refusal becomes a blocker and widening the walk returns to the table. Recorded so the trade-off is not rediscovered from code.
- The merged config's `plugin`/`plugin_origins` fields remain accepted and never value-gated. With project config disabled by D7 and global/home-dot roots isolated, a project cannot inject a plugin entry there, so the residual vector is an authenticated org/well-known or managed source declaring a plugin package after inline config merges. That is out of Stage 1 scope and is recorded rather than closed; D8's filesystem scan does not cover it.
- No CLI surface exposes `Skill.available(agent)`, so agent-scoped skill availability is provable only in-session (E1). If E1 cannot be observed during live acceptance, AC6 is not satisfiable by the discovery precheck alone and the task escalates rather than relaxing the criterion.
- OpenCode org/well-known and managed config can merge after inline config and may use network; D13's immediate re-check is the control, while the post-check provider-owned race is documented and bounded.
- If E1 fails (AGENTS.md invisible), E2 fails (auth broken), screen fallback proves unusable, or any marker executes: stop, keep the branch unmerged, escalate to the user; never weaken the boundary to pass.
- Variant claims stay syntactic; only locally verified `opencode-go/gpt-5.6-luna` variants are documented. `brichan-opencode` remains checkout-oriented; installed OpenCode stays out of scope.
- Changes are additive on `feature/opencode-stage1`; rollback is normal commit revert. Live probes use scratch dirs and Brichan-owned panes only; no global mutation, no secrets, no remote writes.
